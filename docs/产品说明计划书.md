# 「两面」产品说明计划书

> 知乎黑客松 2026 参赛作品  
> 项目地址：[github.com/bingxin666/two-sides](https://github.com/bingxin666/two-sides)

## 一、我为什么做「两面」

平时刷知乎时，我经常遇到一种小小的遗憾：一个问题下面明明有很多认真回答，读完以后却只记住了最响亮的那一种声音。不是答案不够好，而是人的注意力很容易被“赞同最多”“语气最笃定”带着走。

所以我做了「两面」：把一个问题下分散的回答，整理成一组可以被核对的判断；再把每条判断展开成一条取向光谱。光谱两端不是预先写好的“正确/错误”，而是由这条判断自身的语义推导出来。用户可以看到不同答主分别站在哪里，也可以点回原回答，自己判断这条归纳有没有道理。

我希望它像一张轻一点的地图：先帮你看见讨论的地形，再把选择权交还给你。

## 二、产品解决什么问题

知乎的价值在于高质量的经验、解释和争论都留在回答里，但信息密度高也带来三个阅读成本：

1. **观点很多，结构不明显。** 同一个回答里可能同时包含结论、前提、例外和反例，读者很难快速分辨大家究竟在争什么。
2. **高赞不等于全貌。** 排名机制能帮助我们找到好内容，却不能替我们呈现少数意见、限定条件和中间立场。
3. **摘要容易失去证据。** 如果只给一句“AI 总结”，用户无法知道它从哪几句话得出结论，也无法检查是否把原意说偏了。

「两面」不替知乎回答排名，也不替用户投票。它做的是一层可回溯的整理：回答仍然是唯一的观点来源，模型只负责提炼、去重和归位。

## 三、核心体验

### 1. 从热榜开始

首页直接展示当日知乎热榜，问题像一条缓慢移动的光幕。用户不需要先学习一个复杂的搜索语法，点开感兴趣的问题即可开始。

产品入口收敛到热榜有两个原因：热榜是知乎社区正在发生的公共讨论，题目边界清晰、每天可复用；同时我们可以提前完成分析，让用户打开问题时直接看到结果，而不是盯着进度条等待模型现场发挥。

### 2. 在问题页先看“大家在争什么”

一条问题会被整理成若干条判断。每条判断显示参与答主数量与分歧度，用户可以先浏览全局，再选择想展开的那一条。

### 3. 展开一条判断，看到取向光谱

光谱固定为五档，但每条判断都有自己的语义轴。例如同样是“要不要换工作”，两端可能是“优先稳定积累”与“优先主动转向”；它不会被粗暴压成统一的正反标签。

每个光谱位置上的答主都保留：

- 知乎昵称、认证与权威等级；
- 支撑归位的连续原话；
- 归位理由；
- 「查看知乎原文」链接。

页面底部提供“看山解读”，用于概括分布中的共同点和分歧点。它是辅助阅读的综述，不替代原回答。

### 4. 登录后获得“与你有关”

用户可通过知乎 OAuth 登录。服务端只保留进程内的短期会话和必要的用户信号，不把 token 暴露给前端。登录后，如果当天热榜中有用户收藏过的问题，或收藏过其中已经进入光谱的回答，页面会显示“与你有关”标记。

这个功能刻意保持克制：我们不希望用户被算法裹挟。

## 四、技术方案

### 1. 总体架构

前端使用 **Vue 3 + Vite + TypeScript + Pinia**，光幕、卡片和钉子使用 CSS/DOM，迷你光谱使用 Canvas 处理高密度圆点和命中检测。后端使用 **Bun + Hono + TypeScript**，数据落在 SQLite，前端静态资源由 Caddy 提供，API 与 OAuth 回调反代到服务端，整体以 Docker Compose 部署。

### 2. 四阶段分析管线

```text
知乎回答样本
    │
    ├─ 01 提取：批量找出“可争议判断句”，每条必须绑定原话
    ├─ 02 归并：合并同一议题的近义表述，保留条件、例外与反例
    ├─ 03 取向：推导本条判断的两端语义轴，为答主归位并生成理由
    └─ 04 综述：优先调用知乎直答生成中立解读，失败时使用配置的外部模型兜底
```

每个 Agent 按职责单独绑定模型，LLM 调用通过 OpenAI 兼容的原生 `fetch` 完成，不锁定单一供应商。提取、归并、取向和综述都有独立的截止时间、重试和限流；单题总预算默认 600 秒，适合无人等待的夜间预生成。

### 3. 为什么采用“按日快照”

每天 00:30 抓取热榜并生成分析，结果以“东八区日期 + qid”写入 SQLite。用户访问热榜题时只读取 `ready` 快照，正常渲染路径不再实时调用模型：

- 页面打开更快，体验稳定；
- 同一道题不会因为访问时刻不同而得到互相矛盾的版本；
- 相同数据不会被重复请求，符合开放能力的额度约束；
- 某一道题失败只标记该题，不拖挂整张热榜。

## 五、与知乎生态的契合度

### 1. 使用知乎已有的公共讨论，而不是另造内容池

项目直接围绕知乎热榜、知乎搜索结果和回答原文工作。热榜负责发现正在发生的话题，搜索负责补足同题回答，最终展示仍然回到知乎原文。用户在「两面」里看到的是知乎社区的观点关系图，而不是脱离社区的泛化问答。

### 2. 把“多元”做成可检查的结构

知乎回答经常有前提和例外。提取阶段只接受能被原文支持的判断，归并阶段不把不同条件强行合并，取向阶段允许中间档，也允许一条回答同时涉及多个议题。这样做是为了保留社区讨论的纹理：少数意见不会因为票数少就被抹平，模棱两可也不必被逼成站队。

### 3. 尊重原作者与平台边界

每个答主节点都附带昵称、认证、原话和原文链接，读者可以一键回到知乎完成完整阅读。产品不复制整篇回答，不把模型生成的句子冒充答主原话，也不把“没有标记”解释成“与你无关”。

知乎开放能力有调用额度，因此项目采用按日缓存、题内去重、并发限流和失败重试；凭证只在服务端环境变量中，日志和前端响应不包含 token、App Key 或授权码。

### 4. 真实数据与开发边界

开发期保留 mock fixture，只用于本地联调和回归测试。线上运行的是 `VITE_API_MODE=live`、`ZHIHU_LIVE=1`、`PIPELINE_MODE=llm`：首页读取真实知乎热榜，分析读取真实回答，结果来自实际生成的按日快照，不用假数据冒充线上结果。若知乎或模型服务暂时不可用，页面会明确显示空态或失败态，并提供可重试入口。

## 六、用户价值与社区价值

对普通读者，它提供一个进入复杂问题的低门槛入口：先看分歧地图，再决定读哪些回答。

对认真答题的人，它让被埋在长文里的限定条件、少数立场和证据链多一次被看见的机会，并且始终把流量导回原文。

对知乎社区，它提供一种“阅读讨论结构”的新方式：不是再做一个排行榜，而是帮助用户理解为什么会有不同答案、分歧发生在哪个前提上。长期积累后，这些按日快照也可以成为观察公共议题变化的时间切片。

## 八、写在后面

这里是三月七。

这次是我第一次参加黑客松，一开始，我们想做的是另一个产品：连接两个人，通过互相关注的问题，寻找这两个人的交际。

后来由于客观原因，我们换成了两面这样的项目。

这个项目有很多妥协：在 Alpha 和 Beta 测试中，我们都保留了搜索的入口，但在正式上线前，我们选择砍掉了这个功能，只保留了热榜。

这是一个无奈的妥协：实现即时搜索问题 -> Agent 归类 -> 展示，最大的瓶颈在 Agent 上。

不是成本，我们的资金足以覆盖调用模型的成本，以及来自知乎的赞助 Token 也能补足这个问题。

关键在于 token 速度：如果我们希望用户提出一个问题 -> 看到光谱，时间控制在十秒内，那么 token 速度需要在 200 - 300 每秒左右。

可惜的是，除了 Gemini（我们团队不是很信任 Gemini 的幻觉问题...），我们没有找到其他 API 可以实现这个速度，所以这个功能只好被砍掉了。

于是我们又是砍又是临时加功能，最后 Vibe 出来了这样的一个产物。

希望你玩的开心，也希望我们未来也有更多的点子。
